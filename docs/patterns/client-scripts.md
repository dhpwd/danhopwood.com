# Client scripts

## Client scripts and View Transitions

**Problem:** Astro bundles `<script>` blocks in `.astro` components as module scripts, which run once per full page load. With View Transitions (`<ClientRouter />` in `Layout.astro`), navigating swaps the DOM without re-running them, so listeners are never attached to the new nodes. The page looks correct and the handler never fires again. `astro:page-load` fires after every navigation, but on a full page load the router fires the first one from window `load` (`addEventListener("load", onPageLoad)` in `astro/dist/transitions/router.js`), and `load` waits for the async Plausible script, fonts and eager images. Astro's docs don't say so. A listener added only on `astro:page-load` is missing for that whole time, though the page is already readable: a share click sends no event, and a form submit falls through to its native POST.

**Solution:** put the binding in a named init function, make it safe to run twice with a `data-initialized` guard on each node it binds, register it on `astro:page-load` and call it once at module run:

```ts
document.addEventListener("astro:page-load", initShareLinks);
initShareLinks();
```

Each part covers a case the others miss. The module-run call binds the page's nodes on a full load as soon as the document is parsed, and on a first client-side visit to a page whose script is new, since the router runs that script after the swap and before `astro:page-load`. The listener covers every later navigation, when the module doesn't run again. The guard makes the second call each time a no-op, and keeps a node that survives the swap from being bound twice. A listener on `document` or `window` is added once at module scope, outside the init function: init runs at module run and on every navigation, so a listener added inside it would be added again each time. `NewsletterSignup.astro` is the worked example. `ImageZoom.astro` is a second: each run binds every new `#article img`, marking each with `data-zoom`, and binds the dialog's own listener once, behind `data-initialized`. `src/scripts/rule-draw.ts` is a third, for a script that observes rather than binds: one `IntersectionObserver`, created on the first run and disconnected on `astro:before-swap`, with each row's `data-rule` state as its guard. It also shows how to read layout at init. The router restores a reload's scroll position with a smooth `scrollTo` (`html` has `scroll-behavior: smooth`), and a `#hash` load scrolls smoothly too, so both are still under way when the script runs. A script that asks what is in view reads where the page will land (`history.state.scrollY`, or the fragment's element) rather than `scrollY`. `:target` isn't set yet on that first run, so it finds the fragment's element by decoding `location.hash`, inside a `try` for a malformed one. Work that is safe to repeat needs no guard.

**Anti-pattern:** registering the init function on `astro:page-load` alone, which leaves nothing bound until window `load`.

**Anti-pattern for new work:** `is:inline data-astro-rerun`. It does re-run the script, at the cost of TypeScript, import resolution and deduplication. `document` and `window` survive the swap, so a listener the script adds to either is added again on every navigation: `PostDetails.astro` adds its one `document` listener, the progress bar's `scroll` handler, behind a `window.postProgressBound` flag so the visit gets one. `PostDetails.astro` and `BackToTopButton.astro` both take that route, so expect to find it in the tree – prefer the pattern above for anything new, and keep inline scripts for pre-paint state such as the theme flash guard in `Layout.astro`.

**A widget whose state comes from the URL mounts again on each swap rather than persisting.** `transition:persist` carries a mounted node, state and all, into the next page whenever both pages have it, so a swap between two entries of the same page keeps the old state while the URL moves on. `#pagefind-search` in `src/pages/search.astro` is mounted from the URL's `q` on every arrival instead, by the module-run call and on every `astro:after-swap`. The instance it leaves behind isn't destroyed. Pagefind UI's `destroy()` doesn't cancel a pending debounced search, so that search still runs, the destroyed instance then polls for its index every 50ms without end, and it resets the `pagefind.js` module the next instance shares. Left alone, the old instance is garbage-collected once its last search ends. A module-level reference to anything that closes over the root keeps it alive, so `cancelRestore` drops the restore's `observer` as well as disconnecting it. Leaving starts at `astro:before-preparation`, which the router fires in the `popstate` task on a Back or Forward. By then the browser has moved `location` and `history.state` to the entry being moved to, while the old root stays in the page until the swap, so `isConnected` can't tell a root being left. `search.astro` keeps the root whose page is current in a module-level `live`, set by `initSearch` and cleared at `astro:before-preparation` only when `navigationType` is `"traverse"`, and its writes to the history entry go through `replaceEntry(root, …)`, which drops each one unless its root is still live. That covers a library callback that fires while the router fetches or after the swap (`processTerm` here), the visitor's own input in that window, and `initSearch` after its idle wait and import, which mounts only on a live root. A link moves the URL only at the swap, and a link whose response the router hands back to the browser (`/rss.xml`) fires `astro:before-preparation` and never swaps, so clearing `live` on every navigation would leave a page restored from the back/forward cache with no live root. The one direct write is the in-page link listener's put-back of the entry's own state (see "In-page links after `replaceState`"), since dropping it would leave the entry with null state. That listener returns before `preventDefault()` while no root is live, and leaves the click to the router. One move escapes `live`: a Back from a `/search` entry whose URL has a hash (left by the skip link, with nothing typed since), followed by a Forward to it before the swap, is the router's in-page move, which fires neither event, so `live` stays null until the next swap.

**When to use:** any component that attaches client-side event listeners, and any widget whose state comes from the URL.

## Scroll position and View Transitions

**Nothing scrolls on** `astro:after-swap`**.** The router scrolls a new page to the top, or restores the saved position on a Back or Forward, before it fires `astro:after-swap`. A `scrollTo` in that event undoes the restore, and a listener on `document` keeps doing so on every later page. `src/scripts/restore-scroll.ts` makes the restore jump rather than glide, because the router's `scrollTo(x, y)` otherwise takes `html`'s smooth `scroll-behavior`. A reload's restore, and a Back or Forward within one page after a `#hash` link, don't fire the swap events and still glide. Astro 7.4.3 and later pass `behavior: "instant"` to the router's restores themselves, on a Back or Forward and on a reload (withastro/astro#18506), so `restore-scroll.ts` and its `<script>` tag come out in the upgrade to Astro 7.

**A page that renders its content after the swap restores its own position.** The router's restore lands on the short page and is clamped to it, so the page holds the saved position and scrolls there itself once the content has loaded. It reads the position from `history.state` at `astro:before-preparation`, which the router fires in the `popstate` task, and when its script first runs, never later. Once the router has moved to the entry, `scrollend` writes the current position into `history.state`, so a scroll that ends on the page being left while the router fetches, and the router's `scrollTo(0, 0)` on the swap, each overwrite the saved one. The page ends a restore still waiting on the page being left at `astro:before-preparation`, since one that ran while the router fetches would scroll the old page and write into the new entry, and applies the held position at `astro:before-swap`. `src/pages/search.astro` is the worked example, and it also restores the number of Pagefind results that were showing. A write that adds a key to `history.state` skips an entry whose state is `null`, as the router's own scroll save does. Such an entry is a fragment navigation the router didn't make, such as a hash typed in the address bar, and a key alone gives it state with no `index`, which the router then reads on a Back or Forward and counts from as `NaN`.

**When to use:** any script that scrolls the page, and any page that renders its content after the swap.

## In-page links after `replaceState`

**Problem:** the router decides whether a link stays on the page by comparing it with the URL it last navigated to (`originalLocation` in `astro/dist/transitions/router.js`, compared on `pathname` and `search`), not with `location`. A script that rewrites the URL with `history.replaceState` moves `location` without the router seeing it, so a `#fragment` link on that page resolves to a URL the router takes for another page. It fetches the page again, adds a history entry and swaps, and the URL loses the fragment. A widget mounted on each swap loses whatever the visitor built up. `data-astro-reload` on the link avoids the fetch, but the browser's fragment navigation then adds an entry with no `history.state`, and the router ignores a `popstate` to such an entry: follow a link from there and Back shows the fragment entry's URL over the page just left. Astro 7.4.13's router still works this way.

**Solution:** the page that calls `replaceState` handles its own in-page links. A capture-phase `click` listener on `document` takes a plain click on an `a[href^="#"]` link and calls `preventDefault()`, which the router's own listener respects. It then calls `location.replace(link.href)`, a fragment navigation in the same entry that scrolls to the target and moves the sequential focus starting point there, so the next Tab lands inside it. A fragment navigation clears `history.state`, so the listener puts back the state it read beforehand. The move replaces the entry rather than adding one, unlike the router's in-page move on other pages: an added entry would carry a URL the router misjudges in the same way, so Back to it would fetch the page again. `src/pages/search.astro` is the worked example, where Pagefind's `processTerm` mirrors each search into `?q=`.

**When to use:** any page whose script calls `history.replaceState` with a new URL. Only `/search` does today.

## Browser storage can throw

**Problem:** reading `localStorage` or `sessionStorage` throws a `SecurityError` where the browser blocks site data (all cookies blocked, measured in Firefox and full Chromium), and `setItem` also throws on a full quota. An unguarded call stops the script at that line. Inside a library callback it breaks the library's own work too: an unguarded write inside Pagefind's `processTerm` stops it returning the term, so search shows no results. Nothing shows in a normal browser or in Playwright's default headless shell.

**Solution:** put every read and every write in a `try`/`catch`. A failed read counts as nothing stored, and a failed write is dropped, so the page behaves as it would for a first-time visitor. `src/scripts/theme.ts` is the worked example (`readStoredTheme()`, and the write in `setPreference()`). The inline pre-paint script in `Layout.astro` can't import, so it guards its own read. Test with all cookies blocked, as the blocked-storage bullet in `docs/patterns/browser-testing.md` describes.

**When to use:** any client script that reads or writes browser storage. First check that the state needs to outlive the page at all.

## Disabling a focused button drops focus

**Problem:** setting `disabled` on the focused element moves focus to `<body>`, and re-enabling it doesn't bring focus back. A submit button is focused whenever it was clicked or tabbed to, so a handler that disables it while a request runs leaves keyboard and screen-reader users at the top of the document. Nothing visible marks it.

**Solution:** note `document.activeElement` before disabling, and call `focus()` on it once the control is enabled again. Focus returned this way doesn't draw a `:focus-visible` ring after a mouse click. `NewsletterSignup.astro`'s submit handler is the worked example.

Where the form's spec puts focus on the submit button after every submit, call `focus()` on the button itself instead. Noting `document.activeElement` can't deliver that: after Enter in a field it is the field, and Safari on macOS doesn't focus a button on click, so after a click there it is `<body>`. The enquiry form in `cloud-box-setup.astro` does this.

**When to use:** any handler that disables a control while work is pending.

## Starting a click-to-play video at once

**Problem:** a video that starts loading on the press starts late. In Chromium on a 1.6Mbps line with 150ms latency, a 19.7MB file took 1197ms from the press to `playing` with `preload="none"`. `preload="auto"` alone doesn't fix it: Chrome forces it to `metadata` on a cellular connection and to `none` with Data Saver (web.dev, "Fast playback with audio and video preload"), and Safari on iOS loads no media until playback starts (Apple's Safari HTML5 audio and video guide). Nothing plays until the MP4's `moov` header has arrived, and that header holds an entry for every video frame and audio packet.

**Solution:** warm the video up. `Walkthrough.astro` renders it `muted` and `playsinline` with `preload="none"`, so nothing loads without the script, and at init sets `preload="auto"`, calls `play()` and, on the first `playing`, pauses it and returns it to 0. WebKit lets a muted inline video play without a gesture ("New video policies for iOS"). The press unmutes it inside the click handler and plays from a frame already decoded: about 20ms from the press to `playing` on that throttled line, pressed 4s after load. The warm-up is skipped when `navigator.connection?.saveData` is true. The poster is small (1280 wide), since it loads beside the warm-up and shows only until a frame does.

Three things decide whether the warm-up has landed by the press:

- The header's size. Encode with `-movflags +faststart` and keep the header small. ffmpeg writes each packet as its own chunk, so the tables grow with the packet count, and an audio track with more packets a second than the video has frames doubles its own tables: AAC at 48kHz runs 47 packets a second against 30 frames. The walkthrough's audio rate is set for this – see "Vercel Blob" in `docs/external-services.md`. Its 210KB header lands on the throttled line 3.6s after load
- Other media on the page. A decorative video that loads at once competes with the warm-up for the line, so the walkthrough's preview loads once the warm-up has settled, or after 5s if it hasn't
- Bytes at rest. Chrome stops buffering a paused video by itself: with nothing pressed, `/cloud-box-setup` fetches about 3.5MB from the video host in its first 30s

The router builds the next page in a document with no browsing context, where Chromium refuses a video's load ("Media load rejected by URL safety check"), and the element keeps that error once swapped in. `play()` doesn't retry it, so the script calls `load()` on each video before its first `play()`. The walkthrough's preview clips are primed the same way, with a muted `play()` that also makes a phone load them, since a phone holds an unplayed video to its metadata or less.

A page the router swaps out keeps loading its videos, which then take the line from the next page, so the script releases each at `astro:before-swap`: `removeAttribute("src")`, then `load()`.

**When to use:** any video that should start the moment it is pressed.
